# Модель данных и восстановление

Фактическая начальная схема: [001_initial.sql](../migrations/001_initial.sql). Номер миграции хранится в `migrations`; новая миграция выполняется одной транзакцией, существующие файлы после выпуска не редактируются.

| Таблица                  | Назначение и ключ                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------- |
| settings                 | Пауза, cursors, служебные маркеры; key                                             |
| secrets                  | Зашифрованные Telegram session и Google credentials; key                           |
| messages                 | До 20 последних сообщений на чат, текст ограничен; составной account/chat/message  |
| processed_messages       | Очередь и дедупликация, зашифрованные trigger/analysis/clarification; SHA-256 ключ |
| events                   | Связь исходного сообщения с Calendar ID и зашифрованными параметрами               |
| tasks                    | Зашифрованные title/description/dueAt; open/done/cancelled                         |
| registrations            | Зашифрованная форма и значения, хеш одноразового токена, TTL, статус               |
| document_analyses        | Зашифрованный результат и срок удаления                                            |
| auto_reply_state         | Активность владельца, cooldown и суточный счётчик чата                             |
| outbox                   | Зашифрованные уведомления только владельцу, состояние доставки, ID сообщения бота  |
| audit_log                | ID операции, действие, код решения, время; без содержимого                         |
| api_budget / daily_usage | Консервативный резерв USD по месяцам и лимит сообщений по дням                     |

Очередь: pending → running → succeeded / denied / dry_run / awaiting_input / retry → failed. После рестарта running → retry. Сохранённое намерение используется повторно. Вместе с trigger хранится зашифрованный снимок ограниченного контекста: вытеснение старого сообщения из 20-элементного кэша не ломает уже принятую операцию. Служебное уточнение очищает результат классификации и возвращает ожидающую операцию в pending.

Outbox: pending → sending → sent / uncertain. После рестарта sending → uncertain. Только явный 429 повторяется после ожидания. Неопределённые отправки нужно проверить вручную. Регистрация: pending → submitting → submitted / uncertain; pending → rejected, истечение TTL блокирует отправку.

Retention удаляет контекст и результаты документов, очищает завершённые payload очереди и доставленные уведомления. Минимальные tombstones дедупликации остаются, иначе старый update может повторно вызвать действие. Задачи и события сохраняются до удаления владельцем. Срок ожидания незавершённых операций контролируется отдельно от dedup tombstones; см. реализацию prune.

`/forget CONFIRM` удаляет локальную историю, задачи, связи событий, документы, формы, outbox и секреты; сохраняет обезличенные ключи дедупликации и бюджет. Существующие события на Google не удаляются. Для криптографического удаления резервных копий нужен отдельный процесс ротации/уничтожения ключа.

## Бэкап

Для подготовленного выключенного модуля рабочих автоответов миграция `005_business_replies.sql` описывает `reply_chats` (охват, исключения, явный выбор, паузы и лимиты), `reply_seen` (ключи дедупликации), `reply_jobs` (зашифрованная серия сообщений, основание, состояние подтверждения/доставки и TTL). К рабочей БД она применяется только при будущем запуске новой сборки; подготовка кода сама по себе модуль не включает.

Business Bot API использует дополнительные очереди и метаданные: `task_meta`, `task_actions`, `task_jobs`, `task_inputs` — номера, версии, архив, дедупликация изменений и очередь задач; `document_jobs` — зашифрованный запрос анализа/подготовленный результат и tombstone; `document_meta` — номер и владелец выжимки. Удаление/retention `document_analyses` каскадно удаляет её метаданные. Завершение анализа очищает file ID из очереди; сырые файлы и извлечённый текст в БД не сохраняются.

Остановить сервис, выполнить `npm run backup -- backups/kronk-YYYY-MM-DD.sqlite` (каталог создать заранее). Команда использует SQLite backup API, а не копирование активного WAL. Сохранить ENCRYPTION_KEY в отдельном защищённом хранилище; без него резервная БД не восстанавливается. Mock-ключ тоже нужен для mock-бэкапов. Не хранить `.env` рядом с архивом.

Восстановление: остановить сервис, сохранить текущую БД с WAL/SHM отдельно, восстановить backup как `DATABASE_PATH` в чистый каталог, задать исходный ключ и сначала выполнить `npm run inspect`. Затем запускать один экземпляр. Отдельно проверить uncertain и внешний Calendar. Не объединять старый WAL с восстановленной БД.
