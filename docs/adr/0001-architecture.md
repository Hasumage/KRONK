# ADR 0001: модульный монолит с явной границей исполнения

Дата: 2026-10-25. Статус: принято для MVP.

## Контекст

Один владелец, один процесс, небольшая нагрузка. Важнее предотвратить лишнее действие и дубль, чем ответить на каждое сообщение. Исходное ТЗ: [specification.md](../specification.md). По прямому решению владельца реализуется весь MVP за один цикл; содержащаяся в приложенном документе инструкция остановиться после этапа 1 не используется как отдельное разрешительное правило.

## Решения

Node.js 24, строгий TypeScript, SQLite WAL и модульный монолит. `domain/schema` — проверяемые Zod-контракты; `application/context` и `policy` не вызывают провайдеров; `application/worker` оркестрирует; адаптеры изолируют MTProto, Bot API, OpenAI и Calendar. Отдельный процесс извлекает документы. Chromium запускается только для подтверждаемой регистрации.

SQLite используется через better-sqlite3 и версионированные SQL-миграции вместо ORM. Обоснование допустимой альтернативы: короткие транзакции очереди и outbox проще проверить в явном SQL, миграции атомарны, значения связываются параметрами. Контракты строк БД описаны TypeScript. Для многопользовательского режима потребуются PostgreSQL и отдельные воркеры; текущий процесс блокирует второй запуск на той же БД.

GramJS соответствует выбранному в ТЗ MTProto-стеку. Установленный пакет `telegram` помечен в npm как архивный; версия зафиксирована lockfile. Перед продакшеном проверить совместимость с текущим Telegram, рассмотреть сопровождаемый форк отдельным ADR. Автоматической замены стека не производится.

## Поток

Telegram → проверка аккаунта → минимальный Reply-контекст (до 5 сообщений) → сохранённая очередь → Structured Outputs → независимые проверки policy → dry-run / уточнение / исполнение → аудит → outbox владельца.

Модель не выбирает произвольный инструмент: intent ограничен enum. Ответ проверяется runtime-схемой, источники сверяются с переданными сообщениями, цитата намерения — с исходящим сообщением владельца. Confidence не является разрешением. Политика требует авторство владельца, включённый модуль и валидные параметры. Семантическое распознавание свободных формулировок выполняет модель; mock использует явно заданные фикстуры, а не псевдо-ИИ на регулярных выражениях.

Неопределённое намерение вызывает служебный вопрос; Reply боту или `/clarify ID текст` дополняет исходную операцию. Никаких вопросов собеседнику.

## Надёжность

Уникальный `(account_id, chat_id, message_id)` — дедупликация. SHA-256 от этого ключа — стабильный Calendar event ID: после сбоя выполняется GET, затем INSERT, конфликт 409 читается как уже созданное событие. У задач и результатов документов стабильный первичный ключ операции. Retry до 5 попыток с экспоненциальной задержкой. Классификация сохраняется до исполнения.

Bot API не обеспечивает используемый приложением idempotency key: состояние `sending` после падения становится `uncertain`, автоматического повтора нет. Для автоответов резервирование выполняется до сети, MTProto получает постоянный randomId. Это выбор в пользу отсутствия дублей, допускающий пропущенное уведомление при неоднозначном сбое. HTTP-ошибка/тайм-аут никогда не объявляется успешным действием.

Восстановление Telegram: сохранённые сообщения и задания переживают рестарт. Опрос последних 100 диалогов читает новые сообщения после сохранённого cursor пакетами по 100, не более 500 за один цикл. Первый запуск выставляет baseline без выполнения старых сообщений. Новые во время отсутствия процесса диалоги и диалоги за пределами 100 требуют отдельного решения для гарантированного backfill; полный охват всей истории не заявляется.

## Конфиденциальность

Сессии, OAuth, тексты очереди, задачи, результаты и outbox шифруются AES-256-GCM. В БД открыты только служебные ID, статусы и время. Ключ отдельно через env; локальный автоматически созданный `mock.key` разрешён только mock-режиму. Пароли/коды авторизации не выводятся.

`DRY_RUN=true` блокирует предметные операции, браузер, загрузку документов и исходящие Telegram-сообщения. В `MODE=live` классификация dry-run всё ещё обращается к OpenAI и получает сообщения Telegram; для полностью автономных проверок используется `MODE=mock`.

## Регистрации

Предпросмотр строится локально из структуры формы и профиля: заполнение стороннего DOM до согласия может раскрыть профиль. Подтверждение привязано к домену, точной структуре и значениям; случайный одноразовый токен хранится только хешем, срок жизни ограничен. При изменении формы и неоднозначной отправке — ручная проверка, без повторов.

Поддерживаются только простые бесплатные формы POST без JS, логина, CAPTCHA, файлов, select, textarea и чекбоксов. Форма должна явно содержать признак бесплатности. Только точные разрешённые домены, HTTPS:443, публичные IP; CONNECT-прокси закрепляет проверенный DNS-адрес. Редиректы запрещены. Неизвестные формы завершаются понятным отказом, что допустимо по ТЗ.

## Открытые настройки перед live

Хостинг, ID Calendar, OAuth-аккаунт, ID владельца и токен уведомляющего бота; allowlist чатов/тем, ночное окно; профиль и домены регистраций; retention; модель, проверенные цены и месячный бюджет. Приложение не выбирает аккаунты из подключений среды разработчика.
